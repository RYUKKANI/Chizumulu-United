# 치주물루 오프라인 시험판 사용과 이전 절차

2026년 10월 2일 기준 구현 안내입니다. 기준 코드는 22ac35a이며, 실제 구단 서버에는 아직 새 구조를 적용하지 않았습니다. 훈련 기록, 장부 전체, 수당 발생 내역을 함께 이전합니다. 승인된 설계는 [아키텍처 문서](offline-architecture-v1.1.md)에 있습니다.

## 현지에서 사용하는 방법

출발 전에 인터넷이 되는 곳에서 로그인하고 훈련 회차를 만듭니다. 상단의 원정 준비에서 미전송·충돌·확인 필요 기록이 모두 0인지 확인한 뒤, 현장 사본을 갱신하고 명단을 인쇄하거나 PDF로 저장합니다. 최초 접속과 회차 생성에는 인터넷이 필요합니다.

현장 모드에서 준비된 회차의 출석과 훈련 시간·RPE·메모, 일반 지출을 기록할 수 있습니다. 기기에 저장 중인 상태와 저장이 끝난 상태를 구분합니다. 영수증 사진은 압축해 대기열에 보관하며, 사진이 서버에 올라간 뒤 해당 지출을 보냅니다. 프로필 사진은 최대 384px, 영수증은 최대 1024px로 줄이며 각각 50KiB 이하입니다.

화면을 다시 열거나 연결이 회복되면 전송을 재시도합니다. 앱이 열려 있는 동안 실패 간격을 최대 5분까지 늘려 재시도하며, 수동 동기화도 지원합니다. 앱을 완전히 닫으면 자동 전송은 멈춥니다. 미전송·충돌·확인 필요 기록이 모두 0이고 받기까지 성공했을 때만 완료로 표시합니다.

선수 등록·계약 등 전체 구단 문서 수정, 새 훈련 회차 생성, 경기 기록, 의료 정보 수정, 수당 발생·수정·지급은 온라인에서 처리합니다. 수당은 서버가 미지급액을 확인한 뒤 확정합니다. 오프라인에서 전체 문서를 수정해 온라인 자료의 빈 필드를 덮어쓰지 않도록 막았습니다.

오프라인 사본은 마지막 승인 확인 후 7일 미만일 때만 열립니다. 이 사본으로 로그인 세션이나 관리자 권한을 만들지 않습니다. 권한 거부 응답을 받으면 사본으로 우회하지 않습니다. 세션이 만료되면 같은 계정으로 다시 로그인해야 전송할 수 있으며, 그동안 대기열은 보존됩니다.

미전송 기록이 있는 로그아웃에는 취소, 백업, 같은 계정용 보관, 명시적 삭제 선택지가 있습니다. 보관 후 다시 로그인하면 그 계정의 대기열을 복구합니다. 브라우저 저장 공간을 지우면 기기의 미전송 기록도 사라지므로, 저장 공간 오류가 표시되면 우선 백업합니다. 같은 브라우저의 여러 탭이 대기열을 동시에 바꾸지 못하도록 한 탭만 입력을 맡습니다.

## 의료 정보와 권한

현역 선수의 비상 연락처·알레르기는 승인된 회원 전체가 볼 수 있습니다. 원정용 사본에는 필요한 연락처·알레르기와 확인 출처·날짜만 담습니다. 미확인과 없음은 별도로 표시합니다. 의료 정보는 일반 구단 JSON과 일반 백업에 포함하지 않습니다.

퇴단·이적 등으로 현역 명단에서 빠지면 의료 정보를 별도 보관함으로 옮깁니다. 최초 최종 관리자는 이전 시 지정한 현재 계정이며, 이 계정이 나중에 지정한 승인 회원만 보관함을 온라인으로 볼 수 있습니다. 일반 관리자라는 이유만으로 열람할 수 없습니다. 원정용 사본은 다음 연결 때 정리합니다. 재입단해도 보관 정보를 자동으로 현역 정보에 재게시하지 않습니다.

앱의 일반 백업으로 의료 보관함을 복원할 수 없습니다. 실제 이전 전에 별도 서버 백업과 의료 정보 복구 절차를 운영자가 확보해야 합니다. 오프라인 상태인 기기의 정보를 서버가 즉시 지울 수는 없으며, 최대 사본 기간과 다음 연결 시 권한 검사를 적용합니다.

## 독립된 시험판 실행

Node.js와 pnpm이 있는 개발 환경에서 저장소 루트의 의존성을 설치한 뒤 실행합니다.

```sh
pnpm install --frozen-lockfile
pnpm preview
```

주소는 http://127.0.0.1:8951/ 입니다. 시험 관리자 owner@example.test, 시험 코치 coach@example.test, 공통 암호 TestPassword!10을 사용합니다. 두 선수와 훈련 회차는 가상 자료입니다. 이 서버는 로컬 PGlite와 메모리 사진 저장소만 사용하며 실제 Supabase로 요청을 전달하지 않습니다. 서버를 다시 시작하면 서버 쪽 시험 자료는 초기화되지만 브라우저의 대기열은 남을 수 있습니다.

개발자용 장애 재현은 work/preview-network.json의 offline과 shellOffline 값을 사용합니다. 전자는 API를, 후자는 화면 파일 응답을 차단합니다. 실제 사용자 자료를 이 시험판에 입력하지 않습니다.

## 데이터와 서버 처리

훈련 회차, 훈련 행, 전체 거래 장부, 수당 발생 내역은 별도 테이블을 사용합니다. 기존 선수 ID와 장부 ID를 보존합니다. 같은 날짜·선수에 기존 훈련 행이 여러 개 있으면 합치지 않고 회차 미지정으로 남깁니다. 훈련 계획·본업 일정·다른 구단 영역은 기존 club_state에 유지합니다.

훈련 고유 키는 회차 ID와 선수 ID입니다. 회차 생성은 첫 버전에서 온라인 전용이며 날짜와 번호의 유일 제약을 적용합니다. 오프라인 임시 회차는 후속 기능입니다.

작업은 mutationId, schemaVersion, syncEpoch, kind, targetId, baseRecordVersion, 바꿀 필드의 base와 payload, ownerUserId 및 참고 시각을 갖습니다. 새 행은 버전 0과 행 없음 기준을 보냅니다. 훈련은 수정 전 값·현재 값·새 값을 비교해 서로 다른 필드를 합칩니다. 같은 필드가 다르게 바뀌면 해당 작업 전체를 충돌로 보존합니다. 금융 수정은 기록 버전과 미지급액 등 불변 조건을 확인합니다. 금액은 소수 두 자리 문자열이며 기존 화면과의 호환을 위해 1조 MWK 미만입니다.

apply_club_actions는 최대 50건, 서버 256KiB 이하로 받습니다. 기기는 240KiB 이하로 묶습니다. 예상 가능한 오류는 작업별 applied·duplicate·conflict·rejected 결과로 반환하고, 예상하지 못한 서버 오류는 요청 전체를 되돌립니다. 같은 작업 ID의 재전송은 최초 영수증으로 처리하며 다른 내용에 재사용하면 거절합니다. 작성 권한은 전송 시점의 실제 로그인 계정과 승인 상태로 확인합니다.

모든 도메인 쓰기는 sync_heads 행을 먼저 FOR UPDATE로 잠급니다. 최초 사본은 이 행을 FOR SHARE로 잠근 뒤 읽습니다. 전체 문서를 함께 잠그는 작업도 항상 head 다음 club_state 순서를 지킵니다. 변경분은 changes·nextCursor·hasMore로 페이지별로 받으며, 행과 커서를 기기에 한 번에 저장합니다. 쓰기 응답 순번만 보고 받기 커서를 건너뛰지 않습니다.

사진은 비공개 club-media 버킷에 새 경로로만 업로드합니다. 수정·삭제 권한은 일반 회원에게 주지 않습니다. 브라우저 사진 사본은 계정별 최대 100개이며, 의료 정보·인증 응답·비공개 API 응답은 서비스 워커 캐시에 넣지 않습니다. 불필요한 서버 사진의 정리는 별도 관리자 운영 작업입니다.

## 실제 서버로 이전하는 순서

1. 별도 Supabase 시험 프로젝트에 SQL 파일을 이름 순서대로 적용합니다. 기존 초기 파일 다음에 다섯 개의 20261002 파일이 옵니다. 새 파일은 Supabase CLI migration new로 생성했습니다. 서비스 역할 키는 화면 코드에 넣지 않습니다.
2. 실제 PostgreSQL 연결 두 개로 동시 지급·순번 확정 순서·사본 읽기 잠금을 검사합니다. 실제 Storage의 접근 정책·용량 제한과 Supabase 보안·성능 검사도 확인합니다. 이 단계는 아직 수행하지 않았습니다.
3. 시험 서버에서 실제 iOS·Android 기기의 원정 준비, 새로 열기, 7일 경계, 사진, 저장 공간 부족, 서비스 워커 업데이트를 검증합니다. 첫 접속 전체 전송량과 한 시간 켜 둔 전송량도 측정합니다.
4. 실제 서버의 원본 백업과 별도 의료 서버 백업을 확보합니다. 새 화면과 호환 서버를 먼저 배포하되 sync_heads.enabled=false로 두어 기존 저장 경로를 유지합니다. DB 파일을 설치한 것만으로 자료 이전이 시작되지는 않습니다.
5. 원정이 없는 기간을 정하고 모든 입력자의 기기에서 미전송 0건을 직접 확인합니다. 모든 기기가 새 화면을 받은 뒤 관리자 자료 이전 메뉴에서 조건을 확인합니다. 화면 안내만으로 쓰기를 막지 않고 서버 maintenance 플래그를 켭니다.
6. 원본 revision과 최종 관리자 계정을 지정해 admin_activate_offline을 실행합니다. 서버는 원본을 보존하고 한 트랜잭션에서 이전합니다. 같은 성공 요청을 다시 보내도 재이전하지 않습니다.
7. 선수 ID·훈련 행 수·거래 수·수당 수·잔액·미지급액·회차 미지정 행·의료 열람 권한을 원본과 대조합니다. 확인 후 maintenance를 해제합니다. 실패하면 원본과 오류를 보존하고 관리자 복구 버튼으로 쓰기 중지를 해제할 수 있습니다.
8. 두 계정으로 현장 기록과 프로필 수정이 서로 덮어쓰지 않는지 확인하고 첫 실제 원정을 관찰합니다. 구버전 전체 저장은 이전된 영역을 쓸 수 없도록 서버에서 차단합니다.

서버 전환 후 발견된 구버전 초안은 자동으로 버리지 않습니다. 최초 처리 영수증 또는 정확한 이전 기준 revision에 해당하면 처리 완료 확인이나 훈련·장부 작업 변환을 돕습니다. 그 밖의 초안과 프로필 변경은 원본을 남겨 검토합니다.

## 백업 복원과 앱 업데이트

관리자의 완전한 구단 백업 복원은 서버에서 검증하고 원자적으로 적용합니다. 새 syncEpoch를 발급하므로 기존 기기의 작업을 새 자료에 조용히 적용하지 않고 검토로 보존합니다. 현장 사본은 전체 복원 자료로 쓸 수 없고, 같은 계정의 미전송 기록 복구에만 사용합니다. 의료 정보는 일반 복원으로 덮어쓰지 않습니다.

서비스 워커의 새 버전은 기다렸다가 사용자가 업데이트를 선택할 때 적용합니다. 입력 폼이나 미전송·충돌·확인 기록이 남아 있으면 적용을 막습니다. 이전 작업 형식의 지원 종료는 최소 14일 전에 공지하도록 서버 제약을 두었습니다. 현재 첫 작업 형식은 지원 종료일이 없습니다. 지원 종료 오류가 나도 대기열을 삭제하지 않습니다.

## 검사 결과와 남은 확인

자동 검사 232개를 통과했습니다. DB 기본 30, 오프라인 DB 70, 기기 대기열 31, 사진 5, 구단 운영 34, 업무 화면 모델 16, 관리 모델 26, 명단 20입니다. 실제 브라우저에서는 휴대폰 폭 화면, 출석·지출·사진, 약한 연결, 화면 파일까지 실패한 상태의 창 닫기와 재실행, 복구 후 한 번만 저장되는 흐름을 확인했습니다.

PGlite는 단일 연결 검사이므로 실제 PostgreSQL의 동시 잠금 시험을 대신하지 않습니다. Storage 정책은 로컬 모형으로 검사했으며 운영 버킷에 적용하지 않았습니다. 기존 Playwright 브라우저 자동 검사기는 이 환경의 자식 프로세스 실행 제한으로 실행하지 못했고, 관리 브라우저에서 주요 흐름을 직접 검사했습니다.

실제 HTTP gzip 응답에서 HTML 본문은 기존 3,660,148바이트에서 88,152바이트로 줄었습니다. HTML만의 97.59% 감소이며 전체 첫 접속이나 한 시간 전송량 측정은 아닙니다. 폰트는 별도 파일로 분리하고 기기 글꼴을 먼저 사용합니다. 실제 기기 일주일 운용, 30분 약한 신호 시험, 전체 전송량, 서버 동시 연결 검사가 끝난 뒤 실제 이전 날짜를 확정합니다.
